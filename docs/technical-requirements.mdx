## 1. Architecture overview

```
 Browser (React SPA, Vite build in dist/)
   │  fetch /api/...  (cookie: koko_session)
   ▼
 Vercel ── rewrites /api/(.*) → api/index.js  (one serverless function, maxDuration 60 s)
   │                                  │
   │                                  ▼
   │                         lib/router.js  ── route table: method, path, permission, handler
   │                                  │          auth.audit() after every write
   │                                  ▼
   │                 lib/*.js domain modules (db, customers, catalog, inventory, resellers, shopify,
   │                 dashboard, auth) and lib/finance/*.js (ledger, reports, expenses, payroll,
   │                 intake, vision, sales, posting, files, money)
   │                                  │
   │                                  ▼
   │                     Neon Postgres (serverless driver over HTTPS; WebSocket Pool for scripts)
   │
   └── static SPA served from dist/; all other paths rewrite to index.html

 External: Shopify (storefront JSON + Dev Dashboard app, read-only) · Anthropic Claude API (vision)
 Local dev: server.js (Express) mounts the same router on API_PORT (default 3002); Vite proxies /api
```

Single deployable: one front-end bundle and one API function. No queues, workers or caches; anything long (backfill, migrations) runs as a Node script from a developer machine.

## 4. API conventions

- **One route table.** `route(method, path, permission, handler)` in `lib/router.js`. Path params use `:name`. Routes are matched in order; put fixed paths (`/finance/intake/approve-ready`) before parameterised ones (`/finance/intake/:id`).
- **Permissions.** `public`, `login` (any signed-in user), or a permission string such as `orders:write`. Unauthenticated → 401; missing permission → 403.
- **Audit.** Every write calls `auth.audit(user, action, entity, entityId, changes)`. Finance writes use the `finWrite` helper, which audits automatically and strips CNICs.
- **Errors.** Throw `HttpError(status, message)` with a sentence the user can act on ("Choose the sales channel"). Postgres check / unique / foreign-key violations become 400 with a readable message.
- **JSON in, JSON out.** camelCase in the API, snake_case in SQL; each module maps rows (`rowToOrder`, `rowToExpense`…).
- **Money.** API sends strings with two decimals for finance (`"23200.00"`) and numbers for CRM screens. Finance arithmetic is integer paisa (`lib/finance/money.js`); SQL uses `NUMERIC`.
- **Dates.** `YYYY-MM-DD` strings. Postgres `DATE` values that arrive as JavaScript Dates are read with local parts (never `toISOString()`), because the server may run outside UTC. "Today" is the Asia/Karachi date.
- **Side effects that must not fail the request** (finance posting after an order save) are wrapped: failures go to `fin_post_exceptions` for a retry.

## 5. Security requirements

| Requirement | Implementation |
| --- | --- |
| Password storage | scrypt with per-user salt; constant-time compare |
| Sessions | 32-byte random token in cookie `koko_session` (httpOnly, SameSite=Lax, Secure in production); only its SHA-256 is stored in `sessions`; 14 days, extended on use |
| Brute force | 5 wrong passwords → locked for 15 minutes |
| Authorisation | Fixed role → permission map in `lib/auth.js`; checked on every route; owner has `*` |
| Data scoping | Reseller users carry `users.reseller_id`; every reseller query filters on it; payments listed to resellers hide reference, notes, reason, creator and files; proof files return 403 to resellers |
| Finance isolation | Finance routes require `finance:*`; only owner and `finance` roles have them |
| Ledger integrity | Postgres triggers: balanced entries at commit, posted entries immutable, period status enforced with owner override, control accounts blocked in manual journals, unique source per event |
| Personal data | CNIC never in lists or audit; from screenshots only names + last 4 digits kept (`lib/finance/vision.js` sanitises again) |
| Secrets | Environment variables only (`.env` locally, Vercel settings in production); never committed |
| Uploads | Allowed types: JPG, PNG, WebP, PDF, CSV, XLSX; max 2.5 MB; de-duplicated by SHA-256 |

## 6. Data and migrations

- **Baseline + forward migrations.** `db/schema.sql` creates the original tables; `db/migrations/NNN_*.sql` add everything since. `node scripts/migrate.js` applies pending files in order, each in its own transaction, recording them in `schema_migrations`. `--status` lists them. **Any other argument also applies** (there is no `--help`): always fingerprint live data before running it.
- **Rules live in the database** where they protect money: generated `balance_due_pkr`, PR orders free (CHECK), ledger triggers, payments ↔ advance trigger, status dates trigger.
- **Before and after every live migration**: fingerprint the business tables (row counts + MD5 of rows over a fixed column list) and compare. Migrations that `UPDATE orders` also fire `orders_touch` and change `updated_at`; disable that trigger inside the migration when a timestamp must not move.
- Full table reference: [database-schema.mdx](./database-schema.mdx).

## 10. Testing

| Suite | Command | What it covers |
| --- | --- | --- |
| Finance | `npm run test:finance` | 48 tests: money, ledger rules (balance, immutability, periods, control accounts), reports (TB = BS, cash flow ties out, equity), expenses, payroll (month-end split), claims, staff payments, intake (classification, duplicates, approval rollback), F3 (payments ↔ advance, revenue, reseller FX, exceptions) |
| UI checks | Puppeteer scripts (outside the repo) | Sign in with a temporary session row; click through flows; screenshots at desktop and phone widths; live checks block non-GET requests |
| Build | `npm run build` | Must pass before every push |

Tests run **serially** (`--test-concurrency=1`) because report tests compare balances before and after. Each test uses its own far-future fiscal year (2093–2099) and run-stamped names so reruns never clash.

**Gaps to close:** no automated tests for CRM modules (orders, inventory, resellers) or React components. Recommended next: API tests for orders and reseller statements on the development database, and a smoke test that signs in and opens every page.

## 11. Performance

- Each request opens no long-lived connection (HTTP driver). Batch related queries; avoid one query per row in loops (the posting engine prefetches active entries per order).
- Lists return at most a few hundred rows; heavier views (ledger) cap at 5,000 lines and ask for a shorter range.
- Long jobs run in batches the browser drives (e.g. "Check everything now" posts 12 orders per request) so each request stays well under 60 s.
- Large PDF images are fetched at 480 px.

## 13. Coding conventions

- Match the surrounding code: small modules, plain functions, comments that explain why.
- User-facing text: plain English, sentence case, no jargon; errors say what to do.
- New UI uses kit components and design tokens, never raw hex values.
- Every new table gets a migration file and a line in the `db/schema.sql` header.
- Money in finance code: integer paisa via `toPaisa` / `fromPaisa`; never floating-point sums.
- One commit per feature or fix on `master`, message `type(scope): summary`, with tests and build passing.
